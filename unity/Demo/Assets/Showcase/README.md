# BRIO: FIRST HARMONIC – an SFX FORGE showcase

A one-level 2D momentum platformer in which **every sound is SFX FORGE at runtime**: 19 sound effects
synthesized from patches written in code, and a song whose layers follow the player's speed. There is
no audio file, texture, model or font anywhere in this folder – the art is generated meshes, the
scene is generated by an editor script.

It exists to be read and copied. The game is small on purpose; the part to take home is
[`Scripts/Audio`](Scripts/Audio), sixteen short files that show the three ways to use SFX FORGE in a
Unity game: **one-shots**, **sounds that follow the game while they play**, and **adaptive music**.

Brio is an original character and First Harmonic an original level: running builds speed, slopes and
loops carry it, a Tuck rolls, a Wind-Up charges a Burst, Woofers throw you, Chimes are collected and
scatter when you are hit, Tuning Forks are checkpoints and the Resonator is the goal.

![The title card, the first loop, a Woofer throw and the two loops of Overdrive](../../../../docs/img/showcase.png)

## Open it and play

1. Open the Unity project `unity/Demo` (Unity 6000.3.8f1).
2. Open the scene `Assets/Showcase/Showcase.unity` and press Play.

| | Keyboard | Gamepad |
|---|---|---|
| Run | Left / Right or A / D | left stick |
| Jump (hold for a full jump, tap for a hop) | Space or Z | a face button |
| Tuck into a roll (while moving) | Down or S | stick down |
| Wind-Up (standing still): hold Down, tap Jump up to six times, let go of Down to Burst | Down + Space | stick down + button |
| Start, and play again on the results panel | Space or Z | a face button |

Sound needs Windows x64 (SFX FORGE's native library). Elsewhere the game runs silent and logs up to
three warnings in the Console (one per kind of component: the effects, the players, the music). No
device and no MIDI connection are needed.

## Check it, test it, rebuild it

Nothing in `Showcase.unity` or `Generated/` is edited by hand: both are written by
`Editor/ShowcaseBuilder.cs`. Headless, from Git Bash (only one Unity process may have the project
open; each run takes one to three minutes):

```sh
UNITY="C:/Program Files/Unity/Hub/Editor/6000.3.8f1/Editor/Unity.exe"   # where your Unity 6000.3 is
PROJECT="$PWD/unity/Demo"                           # run from the repository's root
OUT="$PWD/out"

# CHECK: compile, open the saved scene, run the editor checks. Writes nothing.
"$UNITY" -batchmode -quit -projectPath "$PROJECT" -executeMethod SfxShowcase.Editor.ShowcaseBuilder.Verify -logFile "$OUT/unity-showcase.log"
grep "SHOWCASE:" "$OUT/unity-showcase.log"          # one "SHOWCASE: ok" line per check, then "SHOWCASE: PASSED"

# TEST: the play mode tests of Assets/Showcase/Tests and Assets/SfxDemo/Tests together
"$UNITY" -batchmode -projectPath "$PROJECT" -runTests -testPlatform PlayMode -testResults "$OUT/unity-showcase-playmode.xml" -logFile "$OUT/unity-showcase-playmode.log"
grep -o '<test-run [^>]*' "$OUT/unity-showcase-playmode.xml"
grep "SHOWCASE RUN" "$OUT/unity-showcase-playmode.log"   # where the test pilot was each second, and its launch speeds
```

Exit code 0 is success; compile errors appear in the log as `error CS`.

**Rebuild** after changing the level (`Scripts/Level/LevelLayout.cs`), the sounds
(`Scripts/Audio/SoundLibrary.cs`), the look (`Scripts/Art`) or any installer: in the editor
**SFX Forge > Rebuild Showcase Scene**, or headless

```sh
"$UNITY" -batchmode -quit -projectPath "$PROJECT" -executeMethod SfxShowcase.Editor.ShowcaseBuilder.SelfTest -logFile "$OUT/unity-showcase.log"
```

which rebuilds and then runs the same checks as `Verify`. A rebuild rewrites `Showcase.unity` and
`Generated/ShowcaseMeshes.asset` from top to bottom (a new scene gets new file IDs), so both files
show as changed in git even when nothing visible changed: rebuild when something changed, not to
check. It also makes sure the scene is in the build settings' scene list, the one thing the showcase
touches outside its own folder.

The original demo has its own check, `-executeMethod SfxDemo.Editor.SfxDemoBuilder.SelfTest`. It
regenerates the demo's scene and sets the build settings to that scene alone, so run it BEFORE the
showcase's `SelfTest` if you run both (the showcase's `Verify` checks that its scene is listed; the
PlayMode tests load it by path and do not depend on the list).

The PlayMode tests play the game through the same seam the keyboard uses
(`PlayerBase.InputOverride`, see `Tests/ScriptedInput.cs` and `Tests/RunPilot.cs`).
`ShowcaseTests.cs`: standing at the spawn, cruise speed, jump height, a steep slope carrying a player
who lets go, the Wind-Up and Burst, the hills and the first loop, turning round in a loop's switch, a
Woofer's flight, Chimes collected and scattered, respawns at a Tuning Fork and out of a pit, the low
route, the goal and a restart, and a whole run from start to goal that also measures the two launch
ramps. `ShowcaseAudioTests.cs`: a jump and a Chime are really heard through SFX FORGE, the Wind-Up
rev and the roll hum sound and bend while they play, a section's pattern is cued and held, and the
music's intensity follows speed and drops on a hit.

| `Tests` | The PlayMode tests: `ShowcaseTests.cs` (the game), `ShowcaseAudioTests.cs` (the sound), and what they share. |
| `Docs` | `DESIGN.md` (what the game is), `ARCHITECTURE.md` (how the code is organised, and the rules), and one notes file per discipline: `GAMEPLAY-NOTES.md`, `LEVEL-NOTES.md`, `ART-NOTES.md`, `AUDIO-NOTES.md`. |

The four runtime folders reference only `Scripts/Core`, never each other, and gameplay never calls
SFX FORGE. Outside `Scripts/Audio` the sound is known in exactly two files, `Editor/ShowcaseAudio.cs`
and `Tests/ShowcaseAudioTests.cs`, and called from two lines of `ShowcaseBuilder`
(`ShowcaseAudio.Install` and `ShowcaseAudio.Check`). Delete the folder, those two files and those two
lines and the game is the same game, silent. (This is by construction – no other file has a `using`
for the audio code – and has not been tried by actually deleting them.)

## Use SFX FORGE in your own Unity game

Each step names the file to read here. The files are short and commented for exactly this.

### 0. Install and make a seam

- Add the package to `Packages/manifest.json`:
  `"com.catsplat.sfxforge": "file:<path to>/com.catsplat.sfxforge"`, and reference `CatSplat.SfxForge`
  from the assembly your audio code lives in ([`SfxShowcase.Audio.asmdef`](Scripts/Audio/SfxShowcase.Audio.asmdef)).
- Give your game a place where it says what happened without knowing about sound:
  [`Scripts/Core/GameEvents.cs`](Scripts/Core/GameEvents.cs) is a static class of C# events
  (`Jumped`, `Landed(impactSpeed)`, `ChimeCollected(combo)` …). Gameplay raises them; the audio
  subscribes in `OnEnable` and unsubscribes in `OnDisable`. Anything continuous (speed, rolling) is not
  an event: the audio reads it every frame.

### 1. Write your sounds as patches – [`SoundLibrary.cs`](Scripts/Audio/SoundLibrary.cs)

A sound is an `SfxPatch`: an engine (`Impact`, `UiBlip`, `SciFiFm`, `Foley`, `Wavetable`) and up to 25
values in the order of the device's pages.

```csharp
// FREQ, PITCH ENV, ENV TIME, A, B, NOISE, CUTOFF, RESO, DECAY, CRUSH, then ATTACK, SUSTAIN, RELEASE …
SfxPatch coin = SfxPatch.Create(SfxEngine.UiBlip, 86, 64, 0, 26, 60, 0, 127, 0, 62, 0);
```

`SoundLibrary.cs` wraps that call in `Make(engine, frequency: …, decay: …)` so every number has a
name, keeps one commented patch per effect, and ends in one table: sound, patch, route, the MIDI note
it is tuned to, volume. The header comment explains each parameter; `docs/MANUAL.md` in the repository
has the full reference, and the firmware's factory presets (`sfx-forge/sfx-forge.c`, `PRESETS`) are
good starting points. A bare `new SfxPatch()` has level 0 and is silent: always start from `Create`.

To keep a sound as an asset you can click and tune, put the patch in an `SfxPreset`
(`ScriptableObject`): the builder does that for every entry (`ShowcaseAudio.CreatePresetAsset` in `Editor`).

### 2. One-shots – [`SoundEffects.cs`](Scripts/Audio/SoundEffects.cs)

Two routes, chosen per sound in the library's table ([`SoundRoute.cs`](Scripts/Audio/SoundRoute.cs)):

- **Baked** – for short sounds that fire often and are always the same. Render the preset to an
  `AudioClip` once and play it like any clip:

  ```csharp
  AudioClip clip = preset.Bake(AudioSettings.outputSampleRate, midiNote: 76);   // in Awake; null without the native library
  oneShotSource.PlayOneShot(clip, volume);                                      // in the event handler
  ```

  See `BakeClips`, `PlayBaked`, and how a landing's volume follows its impact speed and the footsteps'
  pitch follows the running speed.
- **Live** – for a sound decided at the moment it plays. An `SfxPlayer` synthesizes it on the spot:

  ```csharp
  sfxPlayer.preset = chimePreset;
  sfxPlayer.Play(velocity, semitones, midiNote);     // each Chime of a combo one step up the scale
  ```

  See `OnChimeCollected` and `PlayScatter`. One `SfxPlayer` holds one patch, so live one-shots go
  through [`LiveVoicePool.cs`](Scripts/Audio/LiveVoicePool.cs): the voice already playing that preset,
  else a silent one, else the oldest.

### 3. Sounds that follow the game while they play – [`ContinuousSounds.cs`](Scripts/Audio/ContinuousSounds.cs)

What a synthesizer gives you that samples cannot. A held patch (SUSTAIN above 0) on an `SfxPlayer` of
its own; start it, then write its four live values every frame:

```csharp
rollHumPlayer.Play(1f, 0f, 40);                                    // hold, as the MIDI note E2   (HeldSound.Hold)
rollHumPlayer.pitchSemitones = speed01 * 12f;                      // 0..24
rollHumPlayer.cutoffOctaves = Mathf.Lerp(-1f, 1.5f, speed01);      // -4..4
rollHumPlayer.level = Mathf.Lerp(0.35f, 1f, speed01);              // 0..1
rollHumPlayer.Release();                                           // let go: it fades over the patch's RELEASE
```

Start a pitched held sound with its MIDI note like any other sound: a bare `Play()` sounds at the
patch's own FREQ, which is rarely in tune with anything (noise such as the wind has no note and is
started with 0). The player glides to each live value over 30 ms, so writing every frame does not click. The file has three
examples: the roll hum (pitch, filter and level from speed), the wind (level and band above 60 % of top
speed) and the Wind-Up rev (retriggered on each tap; pitch, `fm` and filter from the charge).
[`HeldSound.cs`](Scripts/Audio/HeldSound.cs) is the ten lines of hold / let go / retrigger.

### 4. Adaptive music – [`MusicDirector.cs`](Scripts/Audio/MusicDirector.cs)

An `SfxMusicPlayer` plays an `SfxSong` asset (16 sounds and a sequenced song, made on the device or in
the SFX FORGE window). The director turns the game into five calls:

```csharp
music.intensity = …;                        // 0..1, every frame: each instrument plays only at or above its layer threshold
music.CuePattern(2);                        // another pattern of the song, from the next bar line (see below)
music.PlaySound(instrument, velocity, 76);  // a note by hand on one of the song's instruments, on top of the music
music.volume = …;                           // a dip when the player is hurt (not smoothed by the player: ramp it yourself)
music.Stop(); music.Reload(); music.Play(); // the song ends at the goal and starts again with a new run
```

Here intensity follows the player's speed (rising in 0.6 s, falling in 2.5 s, never below a floor per
section), each section of the level has a pattern ([`SectionCue.cs`](Scripts/Audio/SectionCue.cs)),
a checkpoint is answered by three bell notes started on the song's next sixteenth, and the goal stops
the song and plays a fanfare by hand
([`MusicNote.cs`](Scripts/Audio/MusicNote.cs), [`MusicKit.cs`](Scripts/Audio/MusicKit.cs),
[`Pitch.cs`](Scripts/Audio/Pitch.cs)).

What `CuePattern` does depends on the song. A song WITHOUT an arrangement (`SfxSong.ArrangementBars`
is 0), or a pattern that is not in the arrangement, stays on the cued pattern until the next cue. A
song WITH an arrangement – the demo song has one, 16 bars that use all six patterns – jumps to the
arrangement's next bar with that pattern and then walks on through the arrangement, so one cue lasts
one bar. To hold a section's pattern over such a song, cue it again whenever `music.Bar` changes:
`MusicDirector.HoldPattern` is those five lines.

### 5. Put it in the scene – [`AudioInstaller.cs`](Scripts/Audio/AudioInstaller.cs)

`AudioInstaller.Install(player, session, song, presetFactory)` creates the whole `Audio` object in plain
runtime code. Call it from your own scene builder, or follow it top to bottom to do the same by hand
in the Inspector:

| Object | Components | Set |
|---|---|---|
| `Music` | `AudioSource`, `SfxMusicPlayer`, your music script | the `SfxSong`; `playOnEnable` |
| `Effects` | `AudioSource`, your one-shot script | the presets to bake |
| `Effects/Footsteps` | `AudioSource` | nothing: a second source for the baked footsteps, because its pitch follows the running speed |
| `Effects/Live Voice 1…3` | `AudioSource`, `SfxPlayer` | no preset: the pool assigns one per trigger |
| `Continuous` | your script that bends the held sounds | the three players below and the MIDI note of each |
| `Continuous/<sound>` | `AudioSource`, `SfxPlayer` | the held sound's preset; `playOnEnable` off |

Every `AudioSource` is 2D, has no clip and has `playOnAwake` off. `SfxPlayer` and `SfxMusicPlayer` add
their sound to the source beside them and keep it running themselves.

### 6. Take the folder with you

Copy `Scripts/Audio`. From `Scripts/Core` it needs these ten small files and nothing else:
`GameEvents`, `PlayerBase` with the three interfaces it implements (`IPlayerState`, `IPlayerActor`,
`IPlayerInput`) and `TerrainPlane`, `GameSessionBase` with `IGameSession`, `GamePhase` and
`SectionId`. Its assembly definition references the assembly `SfxShowcase.Core` by name: point that
at the assembly you copied them into. Then raise the events from your game – or replace the
subscriptions in each `OnEnable` with your own events and the reads of speed, rolling, grounded and
charge (`ContinuousSounds`, `MusicDirector`) with your own values, and drop the Core files altogether.
`ARCHITECTURE.md` section 7 lists exactly what to replace, and the limits (Windows x64, no
spatialisation for live players, what happens without the native library).
